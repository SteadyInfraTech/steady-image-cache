# Releasing

1. `CHANGELOG.md` keeps an `## Unreleased` section that every pull request with a change a user would notice adds a line to as it merges (fixes, behaviour, settings, metrics, API; not refactors or test-only changes). To release, rename that heading to the version and date (`## 1.0.1 - 2026-11-02`) and add a new empty `## Unreleased` above it. Choose the version from what is in the section: only fixes (and dependency updates) is a patch; a new setting, metric or endpoint is a minor; anything that breaks an existing deployment is a major.
2. In `deploy/daemonset.yaml`, change the image tag to the release tag (for example `:v1.0.1`) and the one README sentence in "Deployment" that names it. If this is the first release that has `/readyz`, also change the readiness probe's path in the manifest from `/healthz` to `/readyz` in the same pull request: the manifest names a released image, and a probe for a path that image lacks marks every pod NotReady. The end-to-end test reads the image name from there, so nothing else needs to change.
   In the same pull request, set the Helm chart's `appVersion` (`charts/steady-image-cache/Chart.yaml`) to the release version without the `v` (`"1.3.0"`), both image tags in its `values.yaml` to the release tag (`"v1.3.0"`), and its `version` to the release version; `helm.yml` refuses to publish the chart when they do not match the tag: the tag publishes the chart as that version (`helm.yml`), and the application version in the package is whatever `Chart.yaml` says.
3. Merge that as one pull request, with CI green: lint, tests and fuzz, `govulncheck`, the multi-architecture image build, the manifest and chart checks (including `promtool`), and every end-to-end job (`e2e`, `e2e-containerd` on both containerd versions, `e2e-operations`, `e2e-helm`). Then look at `main` after the merge: its run is the one that counts, and a flake that appears there is fixed, not rerun away (see `CONTRIBUTING.md`).
4. Tag the merge commit `vMAJOR.MINOR.PATCH` and push the tag. The publish job builds `linux/amd64` and `linux/arm64`, stamps the version into the binary, and pushes `:vX.Y.Z` (and `:latest` for a version without a pre-release suffix such as `-rc.1`). A tag with a suffix is a pre-release and does not move `latest`.
5. Check what the tag published: `docker run --rm ghcr.io/steadyinfratech/steady-image-cache:vX.Y.Z --version` must print the version, and `docker buildx imagetools inspect` must list both platforms. The `Helm Chart CI/CD` run for the tag must show `publish-chart` green (it checks that the chart names the release, waits for the image, and pushes `oci://ghcr.io/steadyinfratech/charts/steady-image-cache`), and `helm pull oci://ghcr.io/steadyinfratech/charts/steady-image-cache --version X.Y.Z` must work. The `End-to-end (public registries)` run for the tag needs the internet and may be throttled by a registry; read its annotations before treating it as a failure of the release.
6. Create the GitHub release from the tag, with the changelog entry as its notes. If a release needs an operator to do something (replace a file, change a setting), the changelog's section for it opens with that, and the release notes repeat it.
7. Leave `deploy/daemonset.yaml` on the release tag: the repository's sample always names the latest release, not the branch build.
8. A release that changes what runs in a way the end-to-end tests cannot see (the chart's publish job, a new base image) can be rehearsed with a pre-release tag such as `vX.Y.Z-rc.1`. The chart check wants `Chart.yaml` (`version`, `appVersion`) and both image tags in `values.yaml` to name exactly that tag, so the rehearsal is a throwaway commit that sets them (not merged) with the tag pushed on it. It builds and publishes the image and the chart under that name and does not move `latest`; delete the rehearsal's package versions afterwards.
